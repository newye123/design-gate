# design-gate

[![tests](https://github.com/newye123/design-gate/actions/workflows/ci.yml/badge.svg)](https://github.com/newye123/design-gate/actions/workflows/ci.yml)
[![license: NC-1.0](https://img.shields.io/badge/license-NC--1.0-orange.svg)](LICENSE)

**设计交付的五阶段闸门 + 一个能跑的检查器。让「我觉得设计好了」变成「这一阶段的产物在第 47 行」。**

```
需求淬炼 → 信息架构 → 线框 → 设计系统 → 对抗审查
```

每个阶段有产物才算过。前面没定，不进下一步。

```bash
git clone https://github.com/newye123/design-gate.git
cd design-gate

python tools/design_check.py docs/设计稿.md                 # 查设计文档
python tools/design_check.py --kind landing landing/       # 查落地页样式
python tools/design_check.py --kind app     frontend/src/  # 查后台界面样式
python -m unittest discover -s tests -v                    # 28 条测试
```

零依赖，Python 3.10+。

---

## 它解决什么

设计交付最常见的病不是「做得差」，是**跳步**：

1. **没定核心任务就开始排页面。** 排完发现三个页面都在做同一件事，或者都不是用户要的那件。
2. **三态漏画。** 空态、加载态、错误态。上线后用户第一次打开看到一片白，或者失败时以为是自己操作错了。
3. **颜色写「柔和的蓝色」。** 这不是 token，是形容词。开发只能猜，猜完返工。
4. **对抗审查没做。** 交付的时候自己觉得挺好，上线第一天被问「点这里会怎样」。
5. **文案里全是「赋能」「闭环」「一站式」。** 这三句话换成任何产品都成立，所以它们等于没说。

五阶段闸门不是流程洁癖，是**把「我觉得」换成「在哪一行」**。

## 三个真实案例

规则是从翻车里长出来的，三个都来自这个工具自己的开发与实跑：

| 案例 | 一句话 | 它证明了什么 |
|---|---|---|
| [01 我写的检查器，在我自己写的好文档上误报了五次](cases/01-five-false-positives.md) | 五次误报，五个不同的「想当然」 | 好样本不误报 + 坏样本必须响，两种探针缺一不可 |
| [02 把闸门对准错的文档，六条「问题」全是我自己的错](cases/02-right-tool-wrong-document.md) | 拿设计闸门查一份调研方案，6 条 finding，0 条真缺陷 | 检查器的第一条规矩是「你检查的是不是这个东西」 |
| [03 同一份代码，两个裁决](cases/03-same-code-two-verdicts.md) | 14 个文件，`landing` 出 5 条 error，`app` 出 0 条 | 会在不同场景下结论相反的规则，必须带显式适用域 |

三份覆盖**三种不同的边界错误**：认错了字 → 认错了对象 → 没有适用域。

## 退出码三档（这是核心设计）

```
0  查过了，没问题
1  查过了，有问题
2  没查成 —— 工具崩了 / 文件读不到 / 对象不对 / 适用域没声明
```

第三档是关键。**一个跑不起来的检查器，绝不许被读成「干净」。**

三种情况都返回 `2`：

```bash
$ python tools/design_check.py 不存在的文件.md
读取失败：... rc=2

$ python tools/design_check.py "docs/调研方案.md"
跳过 ...  命中 2/9 个设计文档标记 —— 闸门对它不适用
rc=2

$ python tools/design_check.py frontend/src/        # 忘了 --kind
检查样式文件时必须声明 --kind landing 或 --kind app。
rc=2
```

如果这三种情况返回 `0`，你会得到一份"全部通过"的报告，而实际上一件事都没查。

## 规则

### G 族：五阶段闸门

| 码 | 查什么 | 级别 |
|---|---|---|
| G001 / G002 | 缺核心任务 / 核心任务没有量化 | error |
| G003 | 缺目标用户 | error |
| G004 / G004b | 缺成功标准 / 成功标准没有可测指标 | error / warn |
| G005 | 缺页面清单 / 信息架构 | error |
| G006 | 缺空态 / 加载态 / 错误态之一 | error |
| G007 | 有颜色章节但没给 hex | error |
| G008 | 全篇没有一个尺寸值（px/rem） | error |
| G009 / G009b | 缺对抗审查 / 对抗审查少于 5 条 | error / warn |
| G010 | 出现禁词 | error |

### D 族：反 AI 味

四条铁律 + 一份禁词表：

| 码 | 查什么 | landing | app |
|---|---|---|---|
| D001 | 用 Inter | warn | warn |
| D002 | 大面积纯黑 `#000` | warn | warn |
| D003 | 三等分网格 | **error** | warn |
| D004 | 居中 Hero | **error** | warn |
| D005 | 文案里的禁词 | error | error |

**`--kind` 必填，没有默认值。** 理由见[案例三](cases/03-same-code-two-verdicts.md)：
同一份代码，`landing` 下 5 条 error，`app` 下 0 条。默认值就是立场，
给了默认值使用者就永远不去想「我在检查什么」。

放宽的只有版式类规则。字体、纯黑、禁词不因页面类型而改变——
**版式是否合理取决于内容密度，字体和文案不取决于。**

## 测试：28 条，四层

```bash
$ python -m unittest discover -s tests
Ran 28 tests in 7.7s
OK
```

| 层 | 守什么 |
|---|---|
| fixture | `good_design.md` 必须零问题通过（`--strict` 下也通过）；`ai_tell.css` 必须 D001–D005 全中 |
| **mutation** | 从合格样本逐条挖掉一个产物，对应规则**必须**响。挖掉还不响，说明这条规则是死的 |
| 退出码 | 真跑子进程，断言 `0 / 1 / 2` 三档 |
| 适用域 | 同一份代码，`--kind` 不同必须得到不同裁决 |

**mutation 层是主体。** 合格样本通过只证明"不误报"，
挖掉东西还通过就说明"这条规则根本不会响"——而一个永远不响的检查器，
对什么都说好，比没有检查器更危险。

这一层实际抓到过一个真漏洞：G002（核心任务没有量化）的实现取了 14 行窗口，
14 行足够跨进下一节，于是窗口里永远有数字，**规则永远不响**。
只靠"拿真实文档跑一遍"永远发现不了——因为真实文档都有数字。

## 它明确不做什么

- **不生成设计。** 它不画线框、不选颜色、不写文案。它只查"该有的有没有"。
- **不判断设计好坏。** 五个阶段的产物齐了、格式对了，它就给 `0`。**齐了不等于好。**
- **不替代对抗审查。** 五问必须人（或模型）逐条答，工具只能数你答了几条。
- **不查交互逻辑。** 点这里会怎样、状态机对不对，静态检查看不出来。
- **不能证明设计可用。** 只有真实用户能证明。

一句话：**这是形式合规的检查器，不是质量的保证。**
形式合规是必要条件，不是充分条件——一份五阶段全齐、但核心任务选错了的设计，
会拿到 `0`，然后失败。
