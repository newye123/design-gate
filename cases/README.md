# 案例索引

三个案例，全部来自 `tools/design_check.py` 的真实开发与实跑，读数在 2026-10-24 复现过。

共同点：**三次翻车都不是"代码写错了"，是"判据的边界画错了"。**

| # | 案例 | 骗你的是什么 | 一句话判据 |
|---|---|---|---|
| 01 | [我写的检查器，在我自己写的好文档上误报了五次](01-five-false-positives.md) | 关键词 | 好样本不误报 + 坏样本必须响，两种探针缺一不可 |
| 02 | [把闸门对准错的文档，六条「问题」全是我自己的错](02-right-tool-wrong-document.md) | 输出格式 | 检查器的第一条规矩是「你检查的是不是这个东西」 |
| 03 | [同一份代码，两个裁决](03-same-code-two-verdicts.md) | 默认值 | 会在不同场景下结论相反的规则，必须带显式适用域，且不能有默认值 |

## 为什么是这三个

不是挑最离谱的，是挑**三种不同的边界错误**：

- **案例一：判据认错了字。** 规则想查"有没有做这一步"，实际查的是"有没有写这几个词"。
- **案例二：判据认错了对象。** 规则是对的，文档是好的，但它们不该碰面。
- **案例三：判据没有适用域。** 规则在两个场景里结论相反，却只有一个答案。

三层依次往内：**词 → 对象 → 语境。**

## 三份案例的公共结构

```
现象      —— 当时跑出来什么
一开始以为 —— 排除掉的错误方向（含为什么排除）
取证      —— 命令原式 + 真实读数
结论      —— 表格对照：「以为的」vs「实际的」
修复      —— 一条规则，不是一条提醒
可迁移的判据 —— 能搬到别的项目去的
```

「一开始以为」这一节不能省。省掉它，案例就变成「我早就知道」，
读者学不到**怎么排除**，只学到**结论长什么样**。

## 怎么用

不要通读。按症状查：

| 你现在的症状 | 看哪份 |
|---|---|
| 检查工具在自己写得不错的文件上报了一堆问题 | 01 |
| 工具报了一批问题，但你怀疑它问错了问题 | 02 |
| 同一份代码，两个环境/两种配置下结论不同 | 03 |
| 想给一个规则加"这个文件跳过"的豁免 | 01（那是最坏的做法） |

## 一个提醒

三份案例里，工具一次都没有"错得离谱"。

它每次都精确地执行了我写的规则，位置报到行，格式像判决书。
**问题全在规则本身**——而规则是我写的，我还觉得自己想得挺周全。

所以这套东西的真正用法不是"相信工具的输出"，是：

> **工具的输出是一份待核清单，不是一份判决书。**

六条 finding 里可能零条是真的（案例二），一条 error 可能该降成 warn（案例三），
两条 error 可能全是工具自己的 bug（案例一）。
