# 案例一：我写的检查器，在我自己写的好文档上误报了五次

> 来源：`tools/design_check.py` 的真实开发过程，2026-10-24 当天，五次误报的读数全部复现过。
> 这份案例讲的不是"工具做出来了"，是**工具的第一版一定是错的**，以及错在哪。

## 现象

检查器写完了，第一件事是拿它去跑一份我自己写的设计文档——
一份我很确定是合格的文档（核心任务、用户、成功标准、页面清单、三态、颜色 token、字号阶梯、对抗审查，一样不缺）。

结果：

```bash
$ python tools/design_check.py docs/第十一章-电路及其应用-大屏课堂包方案.md
[G003] ...  缺「目标用户」——谁在用、什么设备、什么场景
[G004b] ...:29  成功标准里没有可测指标（%／秒／步／率）

检查 1 个文件，规则族 G，error 1 / warn 1
rc=1
```

**两条，都是误报。** 文档里明明有：

```
25:**用户**：
26:- 主用户是老师。课前 5 分钟选模块，课上站在大屏前操作。设备：教室 Windows 电脑 + 投影/希沃一体机…
...
29:**成功标准（可验收）**：
30:1. 上手：打开到第一个模块开始 ≤ 3 次点击，全程不需要鼠标精确操作。
31:2. 备课：每节课只挑 3 个模块，备课 ≤ 10 分钟（每模块自带 30 秒台本）。
32:3. 参与：每个模块内至少 1 次全班动作，老师能在 5 秒内判断多数派。
```

## 取证

取证的方式只有一种：**每一次误报都去核文档原文，找到我的规则漏掉了什么。**
五轮下来，五个根因全不一样。

我把每一次误报都当成一次真实的判据错误来处理：改实现，不加豁免。

### 第一轮：关键词太窄

**规则**：G003 缺目标用户。
**实现**：找 `目标用户` / `用户画像` / `who`。
**实际文档写的是**：`**用户**：`。

一个字的差别。作者用了最自然的写法，我的词表没有它。

**改法**：把词表换成**形态**而不是**词**——
`目标用户 / 用户画像 / **用户** / 用户：/ 受众 / 使用者`。

### 第二轮：只看标题行

**规则**：G004b 成功标准里没有可测指标。
**实现**：`re.search(r"(?:成功标准|验收标准)[^\n]*", text)` —— 只取标题那一行。
**实际**：`**成功标准（可验收）**：` 这一行本身没有数字，数字全在下面四行里。

**根因**：把「标题」当成了「内容」。标题是标签，内容在下面。

**改法**：引入 `section_window()`，取标题 + 其后若干行。

### 第三轮：窗口没有边界

**规则**：G002 核心任务没有量化。
**发现方式**：这一条不是跑真实文档发现的，是**测试**发现的——
我把合格样本里的核心任务改成"提供一个好用的报修功能"（没有任何数字），断言 G002 必须响。
**结果它没响。**

**根因**：第二轮那个窗口固定取 14 行，而 14 行足够跨过「核心任务」那一节，
把**下一节「成功标准」里的数字**也圈了进来。于是核心任务再空洞，窗口里也总有数字。

**改法**：窗口必须有边界——遇到下一个 `##` 标题或下一个加粗标签就停。

这一条最值得记：**它不是误报，是漏报，而且是被测试抓出来的。**
如果只靠"拿真实文档跑一遍"，这个洞会一直留着——因为真实文档都有数字，永远不触发。

### 第四轮：标签必须一字不差

**规则**：G001 缺核心任务。
**实现**：要求 `**核心任务**` 后面紧跟 `：`。
**实际文档写的是**：`**核心任务（写死）**：`。

括号里那三个字是作者在强调"这一句定死了"，恰恰是最强的写法，却被我的正则判成没写。

**改法**：允许标签内带一个短括号 `（…）` / `(…)`。

### 第五轮：换了名字就不认识

**规则**：G004 缺成功标准。
**实现**：认 `成功标准` / `验收标准` / `成功判据`。
**另一份文档写的是**：`**验收指标**（每节记录三个数）：全班动作次数、预测举手率、出口题正确率。`

那三个数就是成功标准，只是作者叫它"验收指标"。

**改法**：词表补上 `验收指标` / `完成判据`。

## 修完之后

```bash
$ python tools/design_check.py --strict docs/第十一章-电路及其应用-大屏课堂包方案.md

检查 1 个文件，规则族 G，error 0 / warn 0
rc=0
```

零问题。同一份文档，同一份代码，从 2 条误报变成 0 条。

## 结论

| 轮次 | 我以为是 | 实际是 | 谁抓到的 |
|---|---|---|---|
| 1 | 文档没写用户 | 词表太窄 | 真实文档 |
| 2 | 文档没写指标 | 只看标题行 | 真实文档 |
| 3 | —— | 窗口越界，永远不响 | **mutation 测试** |
| 4 | 文档没写核心任务 | 标签带括号 | 真实文档 |
| 5 | 文档没写成功标准 | 换了个名字 | 真实文档 |

**两种探针缺一不可**：

- **拿真实的好文档跑** → 抓**误报**（规则太紧）
- **把好文档挖一块再跑** → 抓**漏报**（规则根本不响）

只有前者，你会得到一个永远不响的检查器（它对什么都说好）。
只有后者，你会得到一个见谁咬人的检查器（它对什么都说不）。

## 可迁移的判据

> **判据的正确性，不能靠"我觉得应该这样判"。要靠两种反例：好样本不误报，坏样本必须响。**

三条可以直接搬走的：

1. **写规则时，先问「这个阶段做完长什么样」，再问「它可能怎么写」。**
   关键词表是最脆的东西——同一个概念有五种叫法，作者永远会选你没列的那一种。
   能用形态（标签、标题、表格）就别用词。

2. **任何"取一段文本再判断"的实现，必须显式定义边界。**
   `text[i:i+500]` 这种写法在文档结构上等于随机取样——它会跨节，而跨节就是跨语义。
   边界规则（遇到下一个标题就停）比长度规则（取 14 行）可靠。

3. **误报的正确处理是收窄规则，不是加白名单。**
   我五轮全部改的是规则本身（形态、边界、词表），一次都没有写"这个文件跳过"。
   加豁免是**把问题藏起来**：下一个作者用同样的写法，照样误报，而你已经忘了为什么有这条豁免。

## 一条附带教训

第一轮那两条误报，我一开始的反应是"文档写得不够规范"。

那个反应是错的，而且很危险：**它会让工具倒逼人改文档去迁就工具**，
最后全组都学会写机器爱看的文档，而机器仍然什么都不懂。

**判据是给人用的，不是让人去适配判据。** 文档写法自然、工具认不出来，是工具的错。
