# 案例三：同一份代码，两个裁决。差别不在代码，在你声明它是什么

> 来源：`design_check.py` 在一个真实后台项目上的实跑，2026-10-24，两个读数都复现过。
> 这份案例讲的是**规则的适用域**——一条对的规则，用错地方就是错的。

## 现象

拿反 AI 味规则去扫一个真实后台项目的前端源码（14 个文件）：

```bash
# 默认按落地页处理
$ python tools/design_check.py "frontend/src"
...
检查 14 个文件，规则族 D，error 5 / warn 1
rc=1
```

5 条 error。分别是：

```
[D003] src/pages/AuthPage.tsx:65        三等分卡片
[D003] src/pages/BodyAnalysisPage.tsx:230   三等分卡片
[D003] src/pages/DataEntryPage.tsx:444      三等分卡片
[D003] src/pages/SettingsPage.tsx:325       三等分卡片
[D003] src/pages/WeeklyReviewPage.tsx:256   三等分卡片
[D001] src/styles.css:7                    用了 Inter
```

加一个参数，同一份代码：

```bash
$ python tools/design_check.py --kind app "frontend/src"
...
检查 14 个文件，规则族 D，error 0 / warn 6
rc=0
```

**5 条 error 变成 0 条 error。** 代码一个字没改。

## 一开始以为

看到 5 条 error 的第一反应是：这个项目的版式有问题，五个页面全踩了三等分。

如果照这个结论去改，会做五件事：把每个三列网格改成两列或非对称布局。

**这五件事全都做错了。**

## 取证

去看那五处的实际内容：

```bash
$ sed -n '230p' src/pages/BodyAnalysisPage.tsx
          <div className="grid gap-4 md:grid-cols-3">
```

那是一个**数据看板**里的三列指标卡：体重、体脂、肌肉量。三个指标，
每个一行数字加一句趋势，等宽排列。

再看 `SettingsPage.tsx:325`：

```bash
$ sed -n '325p' src/pages/SettingsPage.tsx
        <div className="grid gap-3 md:grid-cols-3">
```

设置页的三列选项组。

**这些都是后台密集界面的正常排版。**

## 那「禁三等分卡片」这条规则错了吗

没有错。它说的是另一件事。

这条规则的原始语境是**落地页 / 宣传页的首屏**：

```
┌─────────┬─────────┬─────────┐
│  🚀     │  🔒     │  📈     │
│  极速   │  安全   │  增长   │
│ 一句话  │ 一句话  │ 一句话  │
└─────────┴─────────┴─────────┘
```

这个版式之所以是"AI 味"，不是因为三列本身，是因为它同时具备四个特征：

1. **三个卡片的字数几乎相等**（因为是一次生成的）
2. **每张卡配一个 emoji 或线性图标**
3. **标题是两个字的抽象名词**（极速/安全/增长）
4. **正文是一句不承担信息量的话**

三列只是外壳。**真正的问题是"为了填满版式而写内容"，不是"用了三列"。**

后台看板的三列完全相反：每张卡的数字都不一样、都在变、都有下游依赖。
把它判成 AI 味，是**只看了外壳，没看它为什么长这样**。

## 结论

| | 落地页 | 后台界面 |
|---|---|---|
| 三列网格 | 大概率是"填版式" | 大概率是"三个并列指标" |
| 判什么 | 内容是否等长、是否空洞 | 不判 |
| Inter | 是默认字体的信号 | 也可能是刻意选的中性字 |
| 居中 Hero | 信息层级被压平 | 通常没有 Hero |

**同一条规则，在两个适用域里结论相反。**

## 修复：把适用域变成必填参数

第一版没有 `--kind`，默认按落地页处理。这个默认是错的——
它把"最严"当成了"最安全"，实际效果是**在最常见的场景里制造噪音**。

改成显式声明：

```bash
python tools/design_check.py --kind landing landing/    # 落地页：三列 = error
python tools/design_check.py --kind app     frontend/   # 后台：三列 = warn
```

不给会怎样：

```bash
$ python tools/design_check.py "frontend/src"
检查样式文件时必须声明 --kind landing 或 --kind app。
  落地页禁三等分卡片；后台密集界面用三列是合理的。
  同一条规则在两个适用域里结论相反，工具不替你猜。
rc=2
```

**`2`，不是 `0` 也不是 `1`。** 猜不出来就说猜不出来。

两个要点：

**一、`--kind app` 是放宽，不是关掉。**

```
D003  三列网格      landing=error   app=warn
D001  Inter         landing=warn    app=warn    ← 不变
D002  纯黑          landing=warn    app=warn    ← 不变
D004  居中 Hero     landing=error   app=warn
D005  禁词          landing=error   app=error  ← 不变
```

Inter、纯黑、禁词在两种页面里都是问题——**放宽的只有"版式类"规则**，
因为版式是否合理取决于内容密度，而字体和文案不取决于。

**二、`app` 下仍然会报，只是降级为 warn。**

如果 `--kind app` 变成"什么都不报"，那这个参数就成了一个**全局豁免开关**，
和[案例一](01-five-false-positives.md)里说的"加白名单"是同一个错误。

## 可迁移的判据

> **一条规则如果会在不同场景下得出相反结论，那它必须带一个显式的适用域参数，
> 而且这个参数不能有默认值。**

三条：

1. **默认值就是立场。** 不给默认值，用户必须想一次"我在检查什么"；
   给了默认值，用户永远不去想。这个成本应该由使用者承担，不该由工具替他猜。

2. **放宽要分级，不要开关。** error → warn 是放宽；error → 消失是关掉。
   前者保留了"这里值得看一眼"，后者让问题彻底隐形。

3. **判"AI 味"要看内容，不要只看外壳。** 三列、居中、Inter 都只是外壳。
   真正能判的是：这些内容是不是为了填满版式而写的。
   外壳可以自动检，内容只能人看——**所以工具的输出只能是"值得看一眼"，不是"不合格"。**

## 一条附带教训

这个案例最容易被误读成"所以那些规则不用管"。

恰恰相反。同一批代码里，`--kind app` 下仍然留着 6 条 warn，
其中 `styles.css:7` 的 Inter 是真的值得改——那个项目主要界面是中文，
Inter 的中文回退会掉到系统默认字体，字重对不齐，而这个项目有大量数字要等宽对齐。

**噪音和信号在同一份输出里。** 把它们分开的唯一办法是人工看一遍，
而"人工看一遍"这件事，不会因为工具变聪明而消失。
