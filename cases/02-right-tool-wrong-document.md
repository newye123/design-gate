# 案例二：把闸门对准错的文档，六条「问题」全是我自己的错

> 来源：`design_check.py` 对两份真实文档的实跑，读数 2026-10-24 复现。
> 这份案例讲的是**工具用错对象**——比工具写错更常见，也更难发现，
> 因为它的输出看起来完全合理。

## 现象

同一个检查器，跑两份文档，两个截然不同的结果：

```bash
# A：一份设计交付文档（第十一章大屏课堂包方案）
$ python tools/design_check.py --strict "docs/第十一章-电路及其应用-大屏课堂包方案.md"
检查 1 个文件，规则族 G，error 0 / warn 0
rc=0

# B：一份调研与执行方案文档（故事化互动调研与对抗审查）
$ python tools/design_check.py "docs/故事化互动-调研与对抗审查-执行方案.md"
[G001] ...  缺「核心任务」——没有这一句，后面排的页面都是猜的
[G003] ...  缺「目标用户」——谁在用、什么设备、什么场景
[G005] ...  缺「页面清单／信息架构」——没排过结构就直接进视觉，是跳步
[G006] ...  缺空态、加载态、错误态——三态没画出来，这个设计不算完成
[G008] ...  全篇没有一个尺寸值（px/rem）——没有字号阶梯与间距刻度
[G007] ...:191  有颜色章节但没给具体 hex——「柔和的蓝色」不是 token

检查 1 个文件，规则族 G，error 6 / warn 0
rc=1
```

六条。**每一条都是真的"文档里没有"，每一条也都是我不该问的。**

## 一开始以为

第一反应是：这份调研文档写得不够规范，缺了六样东西。

这个反应看起来完全站得住——它确实没有页面清单、没有三态、没有字号阶梯。
按五阶段闸门，它确实一步都没走。

**但这个判断是错的，错在前提。**

## 取证

去看这份文档到底是什么：

```bash
$ head -8 "docs/故事化互动-调研与对抗审查-执行方案.md"
```

它是一份**调研 + 执行方案**：

- 调研部分：竞品形态对照（NOBOOK / 希沃 / 101 教育 PPT）、
  Peer Instruction 的论文依据（Crouch & Mazur 2001、Turpen & Finkelstein 2009）、
  互动深度的 L0–L4 分级
- 执行部分：每集固定七拍、上台协议、任务卡格式、v0.2 的交付与验收表

**它压根不是一份界面设计文档。** 里面没有界面，所以：
没有页面清单是对的，没有三态是对的，没有字号阶梯也是对的。

拿"设计交付闸门"去查一份"调研方案"，就像拿体检表去查一辆车——
每一项都填不上，但车没病。

## 结论

这是这个案例最该做的一步：**逐条核实，不许整批放过。**

| 编号 | 说的是什么 | 真的吗 |
|---|---|---|
| G001 | 缺核心任务 | **不适用**。这是调研+执行方案，它的"任务"是回答"这个方向值不值得做"，不是"这个界面要让人完成什么" |
| G003 | 缺目标用户 | **不适用**。文中 L0–L4 分级和"老师 / 全班"已经界定了对象，只是不叫"目标用户" |
| G005 | 缺页面清单 | **不适用**。没有界面 |
| G006 | 缺三态 | **不适用**。没有界面 |
| G008 | 没有尺寸值 | **不适用**。没有视觉规范 |
| G007 | 有颜色章节但没给 hex | **半真**。文中提到配色方向，但那是"氛围描述"，不是 token。一份调研文档描述氛围是合理的 |

六条里 **0 条真缺陷，5 条不适用，1 条半真但也在适用域外。**

**关键结论：不是文档不合格，是这条命令用错了对象。**

## 为什么会犯这个错

因为**检查器的输出长得像判决书**。

它打印 `[G001] error`，格式和人一样，位置精确到行，还给了退出码 `1`。
人看到这个格式，很容易直接采信——尤其是当它一次报出六条的时候，
"六条问题"这个数量本身就在暗示"这份文档问题很大"。

而真相是：**六条里没有一条在问对的问题。**

这是工具最危险的失效模式——不是给出错误的答案，是**给出格式正确、但问题本身不成立的答案**。
后者更难识别，因为它看起来比前者更可信。

## 修复：让工具先问「这是不是这个东西」

改了两处。

**一、先判文档类型，不对就不查。**

```python
DESIGN_MARKERS = [
    "核心任务", "用户", "页面", "线框", "设计系统", "对抗审查",
    "成功标准", "验收标准", "信息架构",
]
DESIGN_MARKER_MIN = 3

def is_design_doc(text: str) -> tuple[bool, int]:
    hits = sum(1 for m in DESIGN_MARKERS if m in text)
    return hits >= DESIGN_MARKER_MIN, hits
```

命中不足 3 个标记的，跳过并在 stderr 说明原因，不计入 finding。

**二、退出码用 `2`，不用 `0` 也不用 `1`。**

- 返回 `0`（干净）＝ 撒谎，它什么都没查
- 返回 `1`（有问题）＝ 冤枉，把"不适用"说成"不合格"
- 返回 `2`（无法判定）＝ 唯一诚实的答案

改完再跑同一份调研文档：

```bash
$ python tools/design_check.py "docs/故事化互动-调研与对抗审查-执行方案.md"
跳过 ...  命中 2/9 个设计文档标记 —— 闸门对它不适用
被检查的文件都不像设计交付文档。请确认你在检查的是不是设计文档——
对不上的对象，正确退出码是 2（无法判定），不是 0（干净）。
rc=2
```

**六条 finding 变成了零条 finding，退出码从 `1` 变成 `2`。**

注意最后这一句很关键：**这不是"修好了"，是"确认了问错对象"。**
如果退出码变成 `0`，那就是在用"不报错"假装"没问题"。

这条和同作者的另外两个仓库是同一个判据：
**「没跑」和「通过」必须能区分开。**

## 可迁移的判据

> **任何检查工具，第一个要检查的是「对象对不对」，不是「对象好不好」。**

三条：

1. **看到一批 finding，先问「这些规则本来适不适用」，再问「这些 finding 对不对」。**
   顺序反了，你会花一整天修一个根本不存在的问题。

2. **工具要能说「这不归我管」。** 只有"通过 / 不通过"两档的工具，
   遇到不适用的对象时必然说谎——它只能二选一，而两个都是错的。
   必须有第三档。

3. **数量的暗示很危险。** "六条问题"听起来比"一条问题"严重，
   但六条不适用加起来仍然是零。**不要用 finding 的条数当严重程度的代理指标。**

## 一条附带教训

写这个案例的时候我犯过一次同样的错：一开始我把 G004（缺成功标准）也列进了"不适用"，
理由是"调研文档不需要成功标准"。

去核了一下，那份文档第 74 行写着：

```
- **验收指标**（每节记录三个数）：全班动作次数、预测举手率、出口题正确率。
```

**它有成功标准，只是叫"验收指标"。** 于是这一条成了检查器的第五次误报（见[案例一](01-five-false-positives.md)）。

差一点就把一条真实的工具缺陷，写成了"不适用"。
**"不适用"这三个字，是最容易用来掩盖自己错误的结论。**
